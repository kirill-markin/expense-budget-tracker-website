一笔 $4,800 的工资进入 USD 账户。接着，你把 $1,600 兑换成 €1,470，支付 $8 换汇手续费，又在伦敦用旅行卡花了 £96。仅仅一个普通月份，就可能让预算里的收入和支出都被高估，手续费漏记，账户余额也与对账单对不上。

想把**外籍人士多币种预算**做好，每个月都要遵循同样的五条规则：

1. 每个账户都按其实际持有的币种记账。
2. 内部转账的两端都使用实际入账金额。
3. 换汇手续费和银行卡手续费如果单独入账，就分别记录。
4. 月度总额和各预算项目统一采用一种报表币种。
5. 先核对每个账户的原币余额，再看换算后的报表。

![旅行者在果园工作台上用同一架天平称量三罐蜂蜜](/blog/multi-currency-budgeting-for-expats-v2.png)

这样可以分清多币种账目中最容易混在一起的三类事项：

- **支出**：用来支付房租、食品杂货、旅行、手续费和其他成本。
- **资金流转**：在预算范围内的账户之间转移资金。
- **汇率调整**：改变手中外币按报表币种计算的价值。

即使把这三层混在一起，总额看上去仍可能没问题。可信的账本则能让每一层都有据可查。

## 先把每个账户的原币账记准

每个账户都应只有一种原币，例如 USD 支票账户、EUR 活期账户或 GBP 旅行卡。所有已入账变动都按该账户的币种记录，并保留原始正负号。EUR 账户里一笔 €42.10 的食品杂货消费，就应记作一笔 €42.10 的支出。录入时不要用四舍五入后的美元估算值替代它。

刷卡时，账户币种比商家显示的价格更重要。如果伦敦一家商店收取 £96，但这笔交易最终在 USD 卡账户中以 $123.40 结算，就在 USD 卡账本中记录实际入账的 $123.40。如果系统有合适的位置，可以把 £96 保留为来源明细，但不要把一笔 GBP 交易记入持有 USD 的账户。

卡组织也可能在购买日以外的日期完成换汇。[美国消费者金融保护局的信用卡合同术语定义](https://www.consumerfinance.gov/data-research/credit-card-data/know-you-owe-credit-cards/credit-card-contract-definitions/)指出，卡组织可能采用处理外币交易时的汇率，而这个汇率可能不同于购买日或入账日的汇率。境外交易手续费也可能单独出现。遇到这种情况，应把手续费单独记为支出，不要并入估算汇率。

原币金额首先回答一个对账问题：账户余额是否与对账单一致？换算是之后生成的报表视图，不应反过来改写账本。

## 家庭账目统一使用一种报表币种

报表币种是汇总月度收支、净资产和预算项目时使用的统一单位。通常应选择家庭支付大多数账单或做大多数规划决策时所用的币种。例如，住在西班牙的人可能同时持有 USD 和 GBP 账户，但每个月用 EUR 做预算。

这样，每类数字的用途都很清楚：

- 原币显示单个账户里实际发生了什么
- 报表币种显示整个家庭赚了多少、花了多少、持有多少
- 汇率来源和日期说明两者之间如何换算

预算也使用报表币种。房租可以直接按 EUR 规划。未来以 USD 支付的保险账单或以 GBP 计价的旅行费用，可以使用有记录的规划汇率估算为 EUR。把计划金额标记为估算值；实际费用入账后，再采用账本的常规汇率政策。

## 先划清预算包含哪些账户

导入交易或分类之前，先写清楚预算边界。所有需要纳入同一家庭预算并进行对账的账户都应包括在内，即使某个账户主要用于旅行或储蓄。

例如：

| 账户 | 原币 | 在预算中的用途 |
|---|---:|---|
| 美国支票账户 | USD | 工资和 USD 付款 |
| 西班牙活期账户 | EUR | 房租和日常生活 |
| 英国旅行卡 | GBP | GBP 消费 |

这份清单中两个账户之间的资金移动属于内部转账，不是新的收入或支出。向房东、航空公司或商店付款则属于支出，因为钱离开了家庭，用于实际购买。[银行转账算支出吗？](/blog/do-bank-transfers-count-as-expenses/)介绍了银行卡还款、向预算范围外的人转账等边界情况。

即使多个余额都显示在同一个服务商账户中，预算边界仍然重要。把服务商账户中的 USD 余额兑换为 EUR 余额，依然是两个不同币种账户之间的转账。

## 跨币种转账要用一组配对记录

跨币种转账需要两条账本记录：一个账户减少一种币种，另一个账户收到另一种币种。两端都按实际入账金额记录。

假设某服务商将 USD 兑换为 EUR：

| 分录 | 带符号金额 | 类型 | 分类 |
|---|---:|---|---|
| 美国支票账户 | -$1,600 | 转账 | 无 |
| 西班牙活期账户 | +€1,470 | 转账 | 无 |
| 美国支票账户 | -$8 | 支出 | 银行及换汇手续费 |

前两行属于同一个转账事件，金额准确显示了转出和到账的数额。隐含成交汇率为 €1,470 ÷ $1,600，也就是每 USD 兑换 0.91875 EUR。

$8 手续费是真实成本，因此不属于转账配对，只在支出中计入一次。如果服务商直接从兑换所得中扣费，且没有单独记入一笔手续费，就保留两端对账单上的金额。不要凭空添加对账单无法支持的手续费记录。

也不要人为创建一笔 $1,600 的“换汇支出”，再配上一笔 €1,470 的“收入”。这样会把自己账户之间的资金流转算成经济活动，也会淹没预算本来要解释的真实分类。

## 一个完整的 USD、EUR 和 GBP 示例

9 月初，这个家庭的美国支票账户有 $1,000，西班牙账户有 €800，GBP 旅行卡有 £100。

当月发生了这些交易：

1. 工资入账，美国支票账户增加 $4,800。
2. 一笔换汇从美国支票账户转出 $1,600，并向西班牙账户转入 €1,470。
3. 服务商单独记入一笔 $8 手续费。
4. 房租、食品杂货、交通和水电费共计 €1,300。
5. 伦敦的银行卡消费共计 £96。

先按原币核对各账户：

| 账户 | 期初余额 | 已入账变动 | 预期的期末余额 |
|---|---:|---:|---:|
| 美国支票账户 | $1,000 | +$4,800 - $1,600 - $8 | $4,192 |
| 西班牙活期账户 | €800 | +€1,470 - €1,300 | €970 |
| GBP 旅行卡 | £100 | -£96 | £4 |

这些余额应与银行或服务商的对账单一致。报表汇率无法补救一笔漏记的 £12 消费，也无法消除一笔重复记录的 €70 食品杂货支出。

接着，把当月活动换算为 EUR。为便于看清计算过程，这个示例使用仅作说明的指定日期报表汇率：USD 变动按每 USD 兑换 0.92 EUR 计算，旅行消费按每 GBP 兑换 1.17 EUR 计算。

| 报表项目 | 原币金额 | EUR 报表金额 |
|---|---:|---:|
| 工资收入 | +$4,800 | +€4,416.00 |
| 转账的 USD 端 | -$1,600 | -€1,472.00 |
| 转账的 EUR 端 | +€1,470 | +€1,470.00 |
| 换汇手续费 | -$8 | -€7.36 |
| EUR 生活成本 | -€1,300 | -€1,300.00 |
| GBP 旅行支出 | -£96 | -€112.32 |

支出报表包含 €1,300.00 的生活成本、€112.32 的旅行支出和 €7.36 的手续费，总支出为 €1,419.68，不包括两条转账记录。资金流转报表仍可列出这两条记录，以及两端按参考汇率计算后产生的 €2 差额，但不会把任何一端当作收入或支出。

这些汇率只是示例，不应直接复用。报表汇率也不能证明银行、卡组织或转账服务商实际执行了什么汇率。[欧洲中央银行的欧元参考汇率](https://www.ecb.europa.eu/stats/policy_and_exchange_rates/euro_reference_exchange_rates/html/index.en.html)通常在工作日的中欧时间 16:00 左右更新，仅供参考。欧洲中央银行强烈不建议将其用于交易目的。对转账账本来说，事实依据仍是转出的 $1,600 和到账的 €1,470。

## 汇率调整不要计入支出

假设这个家庭月末的原币余额与上表一致，但从月初到月末，USD 对 EUR 走弱了。尽管账户里没有少一美元，剩余 $4,192 按 EUR 计算的价值仍会下降。

这种估值变化属于汇率调整，不是工资、支出或转账手续费。一份实用的多币种月末结算应显示：

1. 各原币的期初余额
2. 按同一套政策换算的收入、支出和转账流量
3. 各原币的期末余额
4. 用于衔接换算后期初价值、期间流量和期末价值的汇率调整

这样就能解释：明明没有对应支出，按 EUR 计算的净资产为什么仍会下降。汇率项目承接估值变化，支出分类则继续反映实际成本。

确定一套汇率政策后，就持续采用。当所需货币对存在时，可以使用中央银行针对具体日期发布的每日参考汇率来生成报表。周末、节假日和缺失数据仍然需要明确的处理规则。不要悄悄用今天的汇率换算更早的交易，也不要凭猜测补上缺失汇率。

## 外籍人士每月都能照做的结账流程

先结清原币账本，再查看合并报表。按这个顺序，可以在换算掩盖账户错误之前发现问题。

1. **确定结账期间。** 选择一个已经结束的对账单区间，并决定账本是否只纳入已入账交易。
2. **按原币核对每个账户。** 期初余额加上所有带符号的已入账变动，必须等于期末余额。
3. **匹配每一对内部转账。** 核对转出金额、转入金额、日期和双方共用的转账参考信息。
4. **把手续费与资金流转分开。** 服务商、银行卡和转账手续费如果单独入账，就记为支出。
5. **检查分类。** 找出未分类消费、被记为收入的退款，以及重复计算的银行卡还款。
6. **换算当期活动，生成报表。** 使用已经确定的汇率来源和日期，不要改动原币记录。
7. **检查缺失汇率和汇率调整。** 无法换算的金额不应悄悄消失，而应让合并总额明确标注局限。
8. **对比实际金额和预算。** 如果经常性外币付款发生了重大变化，就更新未来以报表币种表示的预算项目。

不要一开始就强行让换算后的总额对上。两个账户中的错误可能在换算后相互抵消。[预算与银行余额对账指南](/blog/how-to-reconcile-your-budget-with-your-bank-balance/)提供了更完整的检查清单，涵盖漏记、重复和待入账交易。

## 电子表格也能使用这套模型

采用这套流程，不一定需要专门的应用。只要把账户、交易、转账、汇率和预算数据分开保存，电子表格也能胜任。

每条账本记录至少要有：

- 账户及其原币
- 入账日期
- 带符号的原币金额
- 记录类型，例如收入、支出或转账
- 收入和支出的分类；转账不应有支出分类
- 转账两端共用的转账 ID
- 用于对账的来源标识

把汇率放在单独的表中，以日期、来源币种和报表币种为键，再根据这张表计算报表金额。绝不要用换算后的总额覆盖原币金额。

导入对账单时也应遵守同样的规则：保留源文件，预览解析后的记录，检查正负号和币种，核查可能的重复项，并在映射关系获批后再添加记录。[如何将银行对账单导入支出追踪器](/blog/how-to-import-bank-statements-into-an-expense-tracker/)详细介绍了这套审核流程。

## Expense Budget Tracker 的实现方式

[Expense Budget Tracker 的多币种功能](/features/)采用了这套账本模型：

- 每条账本记录都保存带符号的金额及其原币
- 一笔跨币种转账由同一个 `event_id` 下的两条转账记录组成：来源端为负数，目标端为正数，两端都保存实际金额，且 `category` 设为 `NULL`
- 报表换算在读取时通过每日指定日期的货币对完成
- 仪表盘同时显示各账户的原币余额和报表币种总额
- 预算项目使用报表币种
- 汇率缺失时，受影响的金额会明确显示为无法换算，依赖这些金额的总额也会标记为受缺失汇率影响
- 汇率明细把换算后的资金流与估值调整分开显示

托管汇率数据有明确的币种范围。目前，它通过 ECB 数据支持 USD 以及 BGN、DKK、EUR、GBP 和 TRY；通过俄罗斯中央银行支持 RUB；通过塞尔维亚国家银行支持 RSD；通过乌克兰国家银行支持 UAH。它并不覆盖任意币种。迁移账本或依赖合并总额之前，请逐一确认所需币种是否受支持。

你可以通过托管网页界面、内置聊天、托管 MCP 连接器或 Agent API 维护账本。直接通过 HTTP 使用 Agent 时，从 `GET https://api.expense-budget-tracker.com/v1/` 开始，通过 `/v1/sql/query` 读取，并通过 `/v1/sql/execute` 发送已批准的写入操作。[入门指南](/docs/getting-started/)介绍了可用的接入方式，[API 文档](/docs/api/)则说明了身份验证、工作区选择和允许执行的操作。

它没有原生银行同步功能，也没有原生对账单上传功能。你可以把对账单数据交给 Agent，审核它建议的记录，再让它通过 API 或 MCP 连接器写入已批准的条目。这是一套辅助导入流程，不是被动的银行数据聚合，也不是内置的上传界面。

## 每一笔差额都能解释，再结束月末结算

一款实用的**多币种预算应用**，应该能让你从合并数字一路追溯到 USD 工资、EUR 转账两端的准确金额、单独收取的手续费、GBP 消费，以及每个完成对账的原币余额。电子表格也应该达到同样的标准。

如果你需要**追踪多币种支出**，就保留实际入账金额，配对内部转账，分开记录真实手续费，只在生成报表时换算，并把估值变化排除在支出之外。当每一笔差额都能解释为交易、转账、手续费、汇率缺失或汇率调整时，这份报表才真正可用。
