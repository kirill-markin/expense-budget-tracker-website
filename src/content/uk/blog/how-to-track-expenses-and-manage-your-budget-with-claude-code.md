Робота з трекером витрат у Claude Code має починатися з читання, а не із запису. Ще до того, як перша банківська операція потрапить до реєстру, Claude Code може визначити робочий простір, переглянути актуальну схему, перевірити цільовий рахунок і діапазон дат та показати, що саме планує змінити.

Саме можливість перевірити зміни перед їх внесенням робить термінального агента доречним для такого завдання. Claude Code може працювати з файлом і HTTP-запитами, а фінансові рішення залишаються за вами: який рахунок вибрати, чи є рядок переказом, яка категорія підходить і чи варто взагалі вносити запропоновані зміни.

Так ви отримуєте ШІ-трекер витрат із чітким етапом погодження, а не універсальний фінансовий чатбот.

Expense Budget Tracker підтримує такий процес через прямий Agent API. Підключення починається з однієї загальнодоступної URL-адреси:

```text
https://api.expense-budget-tracker.com/v1/
```

Звідти Claude Code може завершити підключення через одноразовий код з електронної пошти, зберегти отриманий довготривалий `ApiKey` поза пам’яттю чату, переглянути дозволену схему та використовувати окремі ендпоїнти для читання й погоджених операцій запису.

## Що робить це налаштування — і куди потрапляють дані

Claude Code працює у вашому терміналі й може обробляти файл виписки, до якого ви надали доступ на своєму комп’ютері. Однак це не робить увесь процес офлайн або суто локальним.

[Актуальні вимоги Anthropic до Claude Code](https://docs.anthropic.com/en/docs/claude-code/getting-started) передбачають підключення до інтернету. Для автентифікації та обробки запитів моделлю використовується Anthropic або постачальник моделі, налаштований у вашій інсталяції Claude Code. Тому відповідні дані виписки, запити та результати API можуть оброблятися за межами вашого комп’ютера відповідно до умов цього постачальника.

Далі межі відповідальності розділені так:

| Межа | Що там відбувається |
|---|---|
| Ваш комп’ютер | Вихідна виписка спочатку є локальним файлом. Claude Code отримує лише той доступ до файлів, який ви дозволите. |
| Claude Code і постачальник моделі | Claude Code інтерпретує файл, готує запити й пояснює результати. Для автентифікації та обробки запитів моделлю потрібен інтернет. |
| Прямий Agent API | Claude Code надсилає конкретні автентифіковані запити на читання та погоджені операції запису, потрібні для завдання. API не може довільно переглядати файли на вашому комп’ютері. |
| Сховище Expense Budget Tracker | Підтверджені фінансові записи зберігаються в розміщеній у хмарі базі даних або у вашій власній інфраструктурі, якщо ви самостійно розгорнули застосунок. |

Цей процес також відрізняється від віддаленого MCP-конектора для Claude і Claude Desktop. Прямий API використовує довготривалий `ApiKey`, і саме цей шлях описано тут. MCP використовує браузерний OAuth за іншою URL-адресою; саме підключення до нього не надає доступу до локальних файлів.

Якщо для вас насамперед важливо не надавати постійного доступу до банку, стаття [Бюджетний застосунок без підключення до банку](/blog/budget-app-without-bank-linking/) докладніше пояснює ці межі даних.

## Підключіть Claude Code через початкову URL-адресу

Установіть і автентифікуйте Claude Code за [офіційною інструкцією Anthropic](https://docs.anthropic.com/en/docs/claude-code/getting-started). У [довіднику CLI](https://docs.anthropic.com/en/docs/claude-code/cli-usage) описано роботу команд в інтерактивному й неінтерактивному режимах.

Коли `claude` запрацює у вашому терміналі, відкрийте його в каталозі, де зберігаєте фінансові файли, і дайте такий запит:

```text
Підключись до Expense Budget Tracker через https://api.expense-budget-tracker.com/v1/.
Орієнтуйся на службову відповідь API й не припускай деталей ендпоїнтів. Запитай
у мене електронну адресу облікового запису, а потім 8-значний код із вхідних листів.
Збережи отриманий ApiKey поза пам’яттю чату лише після того, як я підтверджу місце зберігання.

Після входу виклич /me, покажи список моїх робочих просторів, попроси мене підтвердити
цільовий робочий простір, збережи його для цього ключа та переглянь /schema.
Поки що не записуй фінансові дані.
```

Актуальна послідовність підключення така:

1. Виконайте `GET https://api.expense-budget-tracker.com/v1/` і дотримуйтесь дій зі службової відповіді API.
2. Укажіть електронну адресу облікового запису, коли Claude Code її попросить.
3. Укажіть 8-значний код з електронного листа. Після успішної перевірки ви отримаєте довготривалий `ApiKey`.
4. Збережіть ключ поза пам’яттю чату, бажано як `EXPENSE_BUDGET_TRACKER_API_KEY` у схваленому вами місці. Не додавайте його до репозиторію.
5. Викличте `/v1/me` і `/v1/workspaces` із заголовком `Authorization: ApiKey <key>`.
6. Виберіть потрібний робочий простір через `POST /v1/workspaces/{workspaceId}/select`.
7. Викличте `/v1/schema`, перш ніж генерувати SQL.

Вибраний робочий простір зберігається для цього ключа. У наступних SQL-запитах можна не вказувати `X-Workspace-Id`, хоча Claude Code усе одно може передати цей заголовок, якщо ви хочете перевизначити збережений робочий простір для одного запиту. Якщо в обліковому записі є рівно один робочий простір, а для ключа ще нічого не вибрано, API може зберегти й використати його автоматично. Проте під час кожної перевірки перед записом варто вказувати назву робочого простору.

Докладний процес автентифікації та рекомендації зі зберігання наведено в розділі [Налаштування ШІ-агента](/docs/agent-setup/).

## Установіть правило перевірки перед першим імпортом

Локальний файл `CLAUDE.md` може зберігати правила роботи для цього фінансового каталогу без самого ключа. Інструкції мають бути короткими й конкретними:

```markdown
# Процес роботи з Expense Budget Tracker

- Починай із https://api.expense-budget-tracker.com/v1/ і переглядай /schema.
- Для кожної операції читання використовуй POST /v1/sql/query.
- Перед записом покажи цільовий робочий простір, точний SQL, очікувану кількість змінених
  рядків, підсумки вихідних даних і можливі дублікати. Чекай на моє явне підтвердження.
- Використовуй POST /v1/sql/execute лише для погодженого без змін запиту INSERT, UPDATE або DELETE.
- Перевіряй кожну операцію запису новим запитом до /v1/sql/query.
- Ніколи не вигадуй балансувальну операцію й не змінюй мовчки категорію, у якій не впевнений.
- Зберігай ApiKey поза цим файлом і поза пам’яттю чату.
```

Додайте справжні назви своїх рахунків, правила категоризації та обробки переказів і валюту звітності, якщо вони сталі. Не копіюйте приклади категорій у трекер лише тому, що вони згадані в статті. Claude Code має запитувати ваші наявні дані й використовувати актуальну схему.

## Імпортуйте одну банківську виписку за допомогою Claude Code

Для першого імпорту безпечніше навмисно обмежити обсяг: один рахунок, одна валюта, один закритий період виписки та файл, рядки якого ви можете перевірити. CSV — вдалий початок, оскільки його структура видима. Для інших форматів спершу потрібно перевірити, як саме з конкретного файлу вилучено дані, і лише тоді довіряти отриманим рядкам.

### 1. Зафіксуйте межі вихідних даних

Перш ніж Claude Code почне розбирати файл, визначте:

- банківський рахунок і відповідний йому рахунок у трекері
- валюту рахунку
- дати першої й останньої проведених операцій у виписці
- початковий або попередній відомий правильний залишок
- кінцевий залишок у виписці
- чи містить файл непроведені операції

Для імпорту та звірки використовуйте проведені операції. Не додавайте непроведені операції до погодженого пакета, доки банк їх не проведе.

### 2. Перевірте цільовий рахунок перед підготовкою рядків

Спершу попросіть Claude Code скористатися ендпоїнтом читання:

```text
Я хочу імпортувати ~/finances/checking-2026-07.csv.

Використовуй лише /v1/sql/query. Підтвердь вибраний робочий простір, переглянь
/v1/schema, покажи доступні рахунки та визнач, який саме рахунок відповідає цій виписці.
Зроби запит до ledger_entries за період виписки й перевір наявні записи за той самий
період. Покажи рахунок, валюту, межі періоду, кількість наявних рядків і всі можливі
дублікати. Нічого не записуй.
```

Основний ендпоїнт читання:

```text
POST https://api.expense-budget-tracker.com/v1/sql/query
```

Він приймає один запит лише для читання: `SELECT` або `WITH ... SELECT`. Тіло запиту містить актуальний SQL, складений на основі `/schema`:

```json
{
  "sql": "SELECT * FROM accounts LIMIT 100"
}
```

Claude Code має обчислювати підсумки та згруповані результати в SQL, а не переносити весь реєстр у розмову. Результат запиту обмежено 100 рядками.

### 3. Перевіряйте попередній перегляд, а не покладайтеся на обіцянку

Попросіть Claude Code перетворити виписку на таблицю для попереднього перегляду, перш ніж створювати `INSERT`. Вона має містити щонайменше рядок із вихідного файлу, дату, суму, валюту, цільовий рахунок, запропонований тип операції та категорію, а також статус дубліката.

Уважно перевірте такі рядки:

- перекази між власними рахунками
- повернення коштів і відшкодування витрат
- зняття готівки та банківські комісії
- незнайомі контрагенти
- операції в іноземній валюті
- рядки на початку й наприкінці періоду виписки
- усі рядки, схожі на наявний запис у реєстрі

Збіг дати й суми може вказувати на дублікат, але не доводить цього. Дві справжні операції можуть мати однакові дату й суму. Якщо джерело містить сталий банківський ідентифікатор, використайте його як додатковий доказ, коли в актуальній схемі є відповідне поле; інакше залиште ідентифікатор у попередньому перегляді, а не намагайтеся будь-що записати його до бази даних.

Потім попросіть стислий підсумок для підтвердження:

```text
Підготуй попередній перегляд імпорту без запису. Покажи:

1. підтверджені робочий простір і рахунок
2. діапазон дат і валюту джерела
3. кількість вихідних рядків і їхню загальну суму з урахуванням знака
4. кожен запропонований рядок реєстру
5. можливі дублікати та непевні класифікації
6. точний запит або запити INSERT, які ти надішлеш
7. очікувану кількість рядків, які буде змінено

Зупинись і чекай на моє підтвердження.
```

### 4. Надішліть лише погоджений набір змін

Основний ендпоїнт запису:

```text
POST https://api.expense-budget-tracker.com/v1/sql/execute
```

Він приймає одну погоджену інструкцію `INSERT`, `UPDATE` або `DELETE`, зокрема підтримувані форми `WITH`. Його навмисно відокремлено від ендпоїнта читання.

Кожен SQL-запит на зміну даних може зачепити не більше 100 рядків. Для довгого імпорту погодьте весь запропонований набір змін до виконання. Спочатку Claude Code має надіслати 1–3 рядки-приклади з такою самою структурою SQL. Якщо цей пробний запит успішний, він має відразу продовжити з рештою погоджених рядків у послідовних пакетах не більш як по 100. Він має відстежувати й перевіряти кожен пакет, але не повинен зупинятися лише для того, щоб попросити вас продовжити або повторно погодити дію. Зміна обсягу, нова неоднозначність або помилка виконання потребують нового погодження.

SQL-інтерфейс не підтримує `ON CONFLICT`, тому дублікати потрібно обробляти явно, а не приховувати за операцією `upsert`.

`POST /v1/sql` досі існує для сумісності й обмежених атомарних сценаріїв із кількома інструкціями. Це не звичайний ендпоїнт для читання виписок або типових операцій запису.

### 5. Зчитайте записані рядки ще раз

Успішна відповідь API — ще не кінець імпорту. Попросіть Claude Code знову зробити запит до відповідного рахунку й періоду через `/v1/sql/query` та порівняти збережений результат із погодженим попереднім переглядом:

- кількість змінених рядків
- дати й суми
- вихідну валюту
- рахунок, до якого прив’язано операцію
- типи операцій і категорії
- кількість дублікатів

Не просіть Claude Code «виправити все, що має неправильний вигляд». Якщо перевірка виявить розбіжність, поверніться до діагностики лише для читання, підготуйте одне конкретне виправлення та підтвердьте його окремо.

Розширений [посібник з імпорту банківських виписок](/blog/how-to-import-bank-statements-into-an-expense-tracker/) описує перекази, повернення, періоди, що перетинаються, та інші рядки, через які зовні коректний імпорт може вводити в оману.

## Звірте один рахунок, перш ніж імпортувати інший

Звірка підтверджує, що рух коштів у реєстрі пояснює банківську виписку. Порівнюйте один банківський рахунок із відповідним рахунком у трекері в тій самій валюті й за той самий період проведення операцій.

Для звичайного депозитного рахунку основна перевірка така:

**очікуваний кінцевий залишок = початковий залишок + проведені надходження − проведені списання**

Якщо рух коштів у трекері записується зі знаком, еквівалентна формула така:

**очікуваний кінцевий залишок = початковий залишок + сума проведених операцій з урахуванням знака**

Рахунки із заборгованістю, як-от кредитні картки, можуть використовувати інші правила знаків. Перш ніж порівнювати числа, попросіть Claude Code назвати виявлене правило.

Скористайтеся запитом, який залишає діагностику в режимі лише для читання:

```text
Використовуй лише /v1/sql/query. Звір імпортований поточний рахунок із кінцевим
залишком у виписці [сума й валюта]. Назви початкову межу періоду та правило знаків.
Якщо залишки відрізняються, покажи точну різницю та перелік рядків, які могли бути
пропущені, дубльовані або записані з неправильним знаком. Не додавай балансувальну
операцію й не змінюй наявні дані.
```

Якщо різниця не дорівнює нулю, перевірте початковий залишок, пропущені або дубльовані операції, перекази, непроведені операції, знаки, дати й валюти. Штучна балансувальна операція вирівнює цифри на екрані, але приховує причину.

Нульова різниця підтверджує, що рух коштів за рахунком сходиться. Вона не доводить правильність категорій. Перш ніж переходити до наступного рахунку, окремо перевірте суми за категоріями. [Посібник зі звірки бюджету](/blog/how-to-reconcile-your-budget-with-your-bank-balance/) докладніше пояснює цю відмінність.

## Аналізуйте витрати через ендпоїнт читання

Коли імпорт перевірено, Claude Code може використовувати `ledger_entries` для аналізу витрат у режимі лише для читання. Сформулюйте запитання точно й попросіть показати SQL, щоб перевірити визначення, за яким отримано відповідь.

```text
Переглянь /v1/schema, а потім через /v1/sql/query порівняй витрати за категоріями
за останні три повні календарні місяці. Визнач точні дати початку й завершення до
написання SQL. Виключи перекази відповідно до збереженого типу операції. Агрегуй
дані в SQL, покажи запит і поясни всі виключені або непевні рядки. Не змінюй дані.
```

Це важливо, адже «витрати» — не універсальний стовпець. Корисна відповідь залежить від актуальної схеми, типів операцій, валюти рахунку, повернень і точних меж дат. Claude Code може написати запит, але ви все одно повинні бачити, що саме увійшло до розрахунку.

Для разового аналізу ставте вузькі запитання, наприклад:

- Які категорії змінилися найбільше між двома повними місяцями?
- Які контрагенти формують загальну суму категорії?
- Чи є можливі дублікати в останньому імпортованому періоді?
- Для яких фактичних категорій немає відповідного бюджетного рядка?

Ліміту в 100 рядків зазвичай достатньо, коли Claude Code групує й фільтрує дані на рівні бази даних.

## Оновлюйте бюджет у Claude Code, не передаючи йому право вирішувати

Для змін бюджету діє той самий процес перевірки, що й для імпорту виписки. Claude Code може прочитати `budget_lines`, порівняти план із фактичними даними реєстру та підготувати `INSERT`, `UPDATE` або `DELETE`. Ви вирішуєте, чи відповідають запропоновані суми вашим планам.

```text
Через /v1/sql/query порівняй фактичні доходи й витрати цього місяця з budget_lines.
Потім підготуй проєкт бюджету на наступний місяць, використовуючи наявні категорії
й актуальну схему.

Для кожного зміненого рядка покажи поточну суму, запропоновану суму, різницю та причину.
Покажи точний SQL і очікувану кількість змінених рядків. Не викликай /v1/sql/execute,
доки я не підтверджу конкретні рядки. Після підтвердженого запису знову зроби запит
до цих рядків, щоб перевірити їх.
```

Не дозволяйте місяцю з великими витратами непомітно перетворитися на новий план. Велика витрата може бути разовою; відсутня категорія може виявитися проблемою в даних; переказ може бути класифікований неправильно. Claude Code здатен показати відмінності, але бюджет у Claude Code усе одно потребує вашого рішення щодо наступних кроків.

## Враховуйте поточні межі Agent API

API надає невеликий набір відношень. Завжди використовуйте `/v1/schema` як актуальне джерело інформації, але зараз поділ доступу на читання й запис такий:

| Відношення | Доступ |
|---|---|
| `ledger_entries` | Читання й погоджений запис |
| `budget_lines` | Читання й погоджений запис |
| `workspace_settings` | Читання й погоджений запис |
| `account_metadata` | Читання й погоджений запис |
| `accounts` | Лише читання |
| `fx_rates_raw` | Лише читання |
| `fx_rates_daily` | Лише читання |

Актуальні обмеження Agent API:

- 100 повернених рядків на один запит
- 100 змінених рядків на одну інструкцію мутації та один запит
- загальний граничний час SQL-запиту — 25 секунд
- 10 запитів на секунду й 10 000 запитів на день для кожного ключа

Політика SQL блокує DDL-команди, як-от `CREATE`, `DROP` та `ALTER`, обгортки транзакцій, коментарі SQL, ідентифікатори в лапках, рядки в доларових лапках, `set_config()` і заборонені функції. Наразі дозволено функції `SUM`, `COUNT`, `MIN`, `MAX`, `AVG` і `COALESCE`. Для пошуку тексту без урахування регістру використовуйте `ILIKE` замість `LOWER(...)`, а замість `NOW()` або `DATE_TRUNC()` — явні діапазони дат. Основні ендпоїнти приймають одну інструкцію на запит. `ON CONFLICT` не підтримується.

Ці обмеження звужують доступні можливості SQL, але не визначають, чи правильна категорія і чи є рядок виписки переказом. Row Level Security ізолює робочі простори на рівні бази даних. Ключі API зберігаються як SHA-256-хеші, і їх можна відкликати в продукті. Однак ви все одно маєте захищати ключ у відкритому вигляді на своєму комп’ютері та перевіряти кожну операцію зі зміни фінансових даних.

Актуальний контракт ендпоїнтів і обмеження наведено в [Довіднику API](/docs/api/).

## Agent API для Claude Code і Claude MCP — це окремі шляхи

У результатах пошуку трекера витрат для Claude часто змішуються термінальні сценарії та конектори для Claude або Claude Desktop. Expense Budget Tracker підтримує обидва варіанти, але їхні налаштування й облікові дані не взаємозамінні.

| | Claude Code з Agent API | Claude або Claude Desktop із MCP |
|---|---|---|
| Найкраще підходить для | Локальних файлів, термінальних сценаріїв, скриптів і прямих HTTP-запитів | Розмов у клієнті Claude з підтримкою MCP |
| Початкова адреса | `https://api.expense-budget-tracker.com/v1/` | `https://mcp.expense-budget-tracker.com/mcp` |
| Автентифікація | Одноразовий код з електронної пошти, потім довготривалий `ApiKey` | Браузерний OAuth |
| Інтерфейс читання й запису | `/v1/sql/query` і `/v1/sql/execute` | Інструменти `sql_query` і необов’язковий `sql_execute` |
| Доступ до локальних файлів | Залежить від файлів і дозволів, доступних Claude Code | Сам віддалений конектор його не надає |

Скористайтеся [документацією MCP-конектора](/docs/mcp-connector/) або повним [посібником із MCP-трекера витрат для Claude](/blog/claude-expense-tracker-mcp-connector/), якщо хочете підключити Claude або Claude Desktop. Продовжуйте використовувати цей сценарій з Agent API, якщо завдання починається з локальної виписки й термінала.

## Готовий запит для всього процесу

Цей запит об’єднує початкове підключення, попередній перегляд, погодження й перевірку в одну послідовність:

```text
Підключись до Expense Budget Tracker через https://api.expense-budget-tracker.com/v1/
і дотримуйся службової відповіді API. Використовуй ApiKey, збережений поза пам’яттю
чату. Виклич /me, покажи список робочих просторів, попроси мене підтвердити цільовий
робочий простір, вибери його та переглянь /schema.

Я хочу імпортувати [шлях до локального CSV] до [рахунку] за [закритий період із датами початку й завершення]
у валюті [валюта]. Спершу через /v1/sql/query перевір рахунок, наявні категорії та записи
ledger_entries за той самий період. Розбери файл і підготуй повний
попередній перегляд. Познач можливі дублікати, перекази, повернення, відшкодування,
комісії, незвичних контрагентів і непевні категорії.

Покажи підсумки вихідних даних, запропоновані рядки, точний SQL і очікувану кількість змінених
рядків. Не записуй, доки я не підтверджу весь набір змін. Використовуй /v1/sql/execute
лише для внесення цих погоджених змін. Для довгого імпорту спочатку надішли 1–3 типові
рядки як пробу. Якщо вона успішна, відразу продовжуй із рештою погоджених рядків
у послідовних пакетах не більш як по 100. Перевіряй кожен пакет через /v1/sql/query,
але не проси повторного підтвердження, якщо тільки не зміниться обсяг, не виникне
нова неоднозначність або не станеться помилка виконання.

Насамкінець звір цей один рахунок із кінцевим залишком у виписці. Якщо вони не
збігаються, поясни різницю, не створюючи балансувальної операції та не змінюючи дані.
```

Почніть з одного рахунку й одного закритого періоду. Якщо попередній перегляд зрозумілий, погоджені рядки після запису зчитуються без розбіжностей, а кінцевий залишок сходиться, ви отримали контрольований процес роботи Claude з особистими фінансами, а не чатбота з нечітким дозволом змінювати ваш фінансовий облік.
